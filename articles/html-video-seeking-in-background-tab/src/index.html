Forcing a video to load in a background tab

The run is triggered by visibilitychange → hidden: a fresh <video> is created and loaded only after the tab is already hidden, with nothing warmed up. Switch to another tab, wait, come back and read the log. The milestone of interest is canplay, and for every milestone the log records whether it fired while hidden or only after the tab became visible again.

Source

Load strategy

blob takes the download away from the media element: fetch() pulls the bytes, and the element only ever sees a blob: URL, which needs neither the network stack nor the disk cache. In Chromium a non-http URL is also exempt from the resource load scheduler (ResourceLoader::StartWith), so nothing can stop or throttle it.

Extra levers (combine freely)

audio: off

An AudioContext may only start inside a user gesture, once per document. Ticking the box is such a gesture, but a box restored from a previous session on page load is not — use the button, or just click anywhere on the page. The lever counts only if the readout says running before the tab goes hidden; a run started with anything else is tagged a instead of A and reports audioKeepAliveState in its summary, so it cannot be mistaken for a run that had audio.


Frame generation

canplay only means the element claims it has data. It does not mean a decoded frame can be read back: a hidden tab can seek fine and still hand out a transparent or uniformly black surface. Every generated frame is therefore inspected, and one carrying no picture at all is logged as frame:BLANK and outlined in red below — that, not canplay, is the pass/fail of the whole approach.
